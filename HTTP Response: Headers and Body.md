# 📥 Task 8: HTTP Response: Headers and Body | استجابة HTTP: الرؤوس والجسم

## 🇬🇧 English Documentation

### 📌 Overview

Following the initial Status Line, an **HTTP Response** provides critical metadata inside its **Headers** and delivers the requested resource inside its **Body**. Understanding how response headers instruct the client browser—and how response bodies structure returned content—is essential for debugging web applications, managing session cookies, and identifying server-side information disclosure.

### 🏷️ HTTP Response Headers

**Response Headers** are `Key: Value` pairs sent by the web server immediately after the Status Line. They inform the browser how to interpret, cache, render, and secure the returned content, as well as how to store session identifiers.

#### Common Response Headers

| Header | Purpose & Example | 
| ----- | ----- | 
| **`Server`** | Identifies the web server software and version handling the request (e.g., `Server: Apache/2.4.54` or `Server: nginx`). | 
| **`Date`** | Indicates the exact timestamp when the response message was generated by the server (e.g., `Date: Wed, 29 Aug 2024 12:00:00 GMT`). | 
| **`Content-Type`** | Specifies the media format (MIME type) and character encoding of the response body so the browser renders it properly (e.g., `Content-Type: text/html; charset=UTF-8`). | 
| **`Content-Length`** | Indicates the exact size of the response body in bytes, allowing the client to verify complete data reception. | 
| **`Set-Cookie`** | Instructs the browser to store a cookie (such as a session token) and send it back on subsequent requests (e.g., `Set-Cookie: session_id=abc123; HttpOnly; Secure`). | 
| **`Location`** | Specifies the target redirect URL when the server returns a `3xx` redirection status code (e.g., `Location: /dashboard`). | 
| **`Cache-Control`** | Defines caching rules for browsers and intermediate proxies (e.g., `Cache-Control: no-store, no-cache`). | 

### 📄 HTTP Response Body

Separated from the headers by a mandatory **Empty Line**, the **Response Body** carries the actual resource or data returned to the client.

#### Common Response Body Formats

1. **HTML Documents (`text/html`):**
   Used to render visual webpages inside the browser.

   ```
   HTTP/1.1 200 OK
   Content-Type: text/html; charset=UTF-8
   Content-Length: 88
   
   <!DOCTYPE html>
   <html>
     <body><h1>Welcome to TryHackMe</h1></body>
   </html>
   
   ```

2. **JSON Payloads (`application/json`):**
   Standard format returned by REST APIs and modern single-page applications.

   ```
   HTTP/1.1 200 OK
   Content-Type: application/json
   Content-Length: 56
   
   {
     "message": "Login successful!",
     "status": "success"
   }
   
   ```

3. **Binary Assets & Media:**
   Includes images (`image/png`), stylesheets (`text/css`), JavaScript files (`application/javascript`), and downloadable documents (`application/pdf`).

### 🛡️ Security Considerations

* **Server Version Disclosure:** Exposing detailed software versions in headers like `Server` or `X-Powered-By` (e.g., `PHP/7.4.3`) helps attackers identify known CVEs and targeted exploits. Servers should be configured to suppress or minimize version banners.

* **Insecure `Set-Cookie` Flags:** Session cookies set without `HttpOnly` can be stolen via **Cross-Site Scripting (XSS)**, while cookies lacking the `Secure` flag can be intercepted over unencrypted `HTTP` connections.

* **Sensitive Data Caching:** Pages displaying confidential data (such as banking details or personal profiles) must include `Cache-Control: no-store` to prevent sensitive response bodies from being saved on shared or local machines.

* **MIME-Type Confusion:** An inaccurate or missing `Content-Type` header can cause browsers to misinterpret uploaded files as executable scripts, leading to **XSS** vulnerabilities.

## 🇸🇦 التوثيق باللغة العربية

### 📌 نظرة عامة

بعد سطر الحالة الأول في استجابة الخادم، تُقدّم **استجابة HTTP** معلومات وصفية بالغة الأهمية داخل **الرؤوس (Headers)**، وتُسلّم المورد أو البيانات المطلوبة داخل **الجسم (Body)**. يُعد فهم آلية توجيه رؤوس الاستجابة لمتصفح العميل—وكيفية هيكلة البيانات المُعادة في جسم الاستجابة—أمراً أساسياً لتشخيص أعطال تطبيقات الويب، وإدارة جلسات ملفات تعريف الارتباط (Cookies)، واكتشاف تسريب معلومات الخادم.

### 🏷️ رؤوس استجابة HTTP (Response Headers)

**رؤوس الاستجابة** هي أزواج من المفاتيح والقيم (`Key: Value`) يُرسلها خادم الويب مباشرة بعد سطر الحالة. تُخبر هذه الرؤوس المتصفح بكيفية تفسير المحتوى المُعاد وعرضه وتخزينه وتأمينه، بالإضافة إلى تعليمات حفظ مُعرّفات الجلسة.

#### أشهر رؤوس الاستجابة

| الرأس (Header) | الوظيفة والمثال | 
| ----- | ----- | 
| **`Server`** | يُعرّف ببرنامج خادم الويب وإصداره الذي عالج الطلب (مثل: `Server: Apache/2.4.54` أو `Server: nginx`). | 
| **`Date`** | يُحدّد الطابع الزمني الدقيق لإنشاء رسالة الاستجابة من قِبل الخادم (مثل: `Date: Wed, 29 Aug 2024 12:00:00 GMT`). | 
| **`Content-Type`** | يُحدّد نوع المحتوى (MIME type) وترميز الأحرف لجسم الاستجابة ليتمكن المتصفح من عرضه بشكل صحيح (مثل: `Content-Type: text/html; charset=UTF-8`). | 
| **`Content-Length`** | يُحدّد الحجم الدقيق لجسم الاستجابة بالبايت، مما يتيح للعميل التحقق من استلام البيانات كاملة. | 
| **`Set-Cookie`** | يأمر المتصفح بتخزين ملف تعريف ارتباط (مثل رمز الجلسة) وإرساله مجدداً في الطلبات اللاحقة (مثل: `Set-Cookie: session_id=abc123; HttpOnly; Secure`). | 
| **`Location`** | يُحدّد رابط الوجهة لإعادة التوجيه عندما يُعيد الخادم رمز حالة من فئة `3xx` (مثل: `Location: /dashboard`). | 
| **`Cache-Control`** | يُحدّد قواعد التخزين المؤقت للمتصفحات والوسطاء (مثل: `Cache-Control: no-store, no-cache`). | 

### 📄 جسم استجابة HTTP (Response Body)

يُفصل **جسم الاستجابة** عن الرؤوس بـ **سطر فارغ (Empty Line)** إجباري، ويحمل المورد الفعلي أو البيانات المُعادة إلى العميل.

#### أشهر صيغ البيانات في جسم الاستجابة

1. **مستندات HTML (`text/html`):**
   تُستخدم لعرض صفحات الويب المرئية داخل المتصفح.

   ```
   HTTP/1.1 200 OK
   Content-Type: text/html; charset=UTF-8
   Content-Length: 88
   
   <!DOCTYPE html>
   <html>
     <body><h1>Welcome to TryHackMe</h1></body>
   </html>
   
   ```

2. **بيانات JSON (`application/json`):**
   الصيغة القياسية التي تُعيدها واجهات البرمجة (REST APIs) وتطبيقات الويب الحديثة.

   ```
   HTTP/1.1 200 OK
   Content-Type: application/json
   Content-Length: 56
   
   {
     "message": "Login successful!",
     "status": "success"
   }
   
   ```

3. **الملفات والوسائط الثنائية:**
   تشمل الصور (`image/png`)، وملفات التنسيق (`text/css`)، وملفات البرمجة (`application/javascript`)، والمستندات القابلة للتحميل (`application/pdf`).

### 🛡️ الاعتبارات الأمنية

* **كشف إصدارات الخادم:** إن إظهار تفاصيل إصدارات البرمجيات في رؤوس مثل `Server` أو `X-Powered-By` (مثل `PHP/7.4.3`) يُساعد المهاجمين على تحديد الثغرات المعروفة المرتبطة بتلك الإصدارات؛ لذا يجب إخفاء أو تقليل هذه المعلومات.

* **ضعف خصائص `Set-Cookie`:** ملفات تعريف الارتباط الخاصة بالجلسات التي تفتقر إلى خاصية `HttpOnly` يمكن سرقتها عبر هجمات **البرمجة عبر المواقع (XSS)**، بينما يؤدي غياب خاصية `Secure` إلى إمكانية اعتراضها عبر اتصالات `HTTP` غير المشفرة.

* **تخزين البيانات الحساسة مؤقتاً:** الصفحات التي تعرض بيانات سرية (مثل الحسابات البنكية أو الملفات الشخصية) يجب أن تتضمن `Cache-Control: no-store` لمنع حفظ جسم الاستجابة الحساس في ذاكرة المتصفح المؤقتة.

* **الالتباس في نوع المحتوى (MIME-Type Confusion):** عدم تحديد رأس `Content-Type` بدقة قد يدفع المتصفح لتفسير الملفات المرفوعة كأكواد برمجية قابلة للتنفيذ، مما يؤدي إلى ثغرات **XSS**.
